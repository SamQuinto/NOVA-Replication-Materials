NOVA replication guide for Appendix C
Updated 29 October 2026

About the package

The replication package brings together the NOVA scorer architectures, the
negotiation exercises, and the data and code used to evaluate them. Researchers
can try NOVA in a downloadable web app, inspect the prompts and scoring rules,
and reproduce the reported analyses without making further paid model calls.
Participant data from the pilot tests have been de-identified before sharing.

This guide expands on the repository README and can help an author write
Appendix C. All paths start from the repository root. The separate architecture
guide explains its own files relative to the architecture folder, so those
instructions still work if the outer supplement folder is renamed.

1. Where to start

The repository has three main folders:

1_Architecture_and_Demonstration contains the Architecture 1 and 2 (A1 and A2)
prompts, scoring code and downloadable web app. Its A1 and A2 subfolders explain
the two approaches and link to the scripts. The code folder includes the files
those scripts need. The detailed architecture guide explains each step and
reproduces the exact prompts and relevant code for Appendix B.

2_Exercise_Materials contains Negotiation_Exercise_Role_Materials.docx and .pdf.
This single document brings together the main job negotiation and the tutorial.
The main task assigns one negotiator to the Candidate role and the other to the
Recruiter role. Both the NOVA version and the fixed nine-issue version are
included. The tutorial is a shorter venue-hire negotiation that participants in
our pilots completed before the main task to become familiar with NOVA.

The scoring_tables subfolder contains the issues, options and scores. The
questionnaires subfolder contains the main-study questions and the earlier
role-feedback surveys. Responses to those questions are in the third folder.

3_Validation_and_Development contains the offer-review spreadsheets, participant
offers and survey responses, saved scorer responses, and the analysis notebook.
Analysis.html is the easiest place to read the results. Analysis.ipynb lets you
run the calculations yourself. Methods.md explains the measures and sample
selection; Data_Dictionary.md explains the files and how they link together.

2. Try NOVA in your browser

Download the repository, or just the complete architecture folder. Keep all the
files in that folder together. Downloading only score_offer.py will not provide
the prompts, exercise definitions and other code it needs.

You will need Python 3.11 or later and your own OpenAI API key to score offers.
Copy .env.example to a file named .env in the architecture folder and replace
the placeholder with your key. Keep that file private. You can also provide the
key through the OPENAI_API_KEY environment variable.

From 1_Architecture_and_Demonstration, run:

    python demo/Start_Demo.py

The downloadable web app opens in your local browser. Choose the exercise,
role and scorer, type an offer, and click Score with API. The app shows NOVA's
interpretation and the scores assigned to each issue. You can edit your offer
and calculate it again without clearing the text. Calls are charged to your
OpenAI account. The app reads your key on your computer rather than exposing
it in the browser or publishing it with the repository.

If you would just like to see how the app works, Try a saved example needs no
key or charge. It loads an existing interpretation and calculates its score;
it does not ask a model to read newly typed text. The web app is for testing
offers, not for pairing participants or running a complete negotiation study.

Only offers submitted for live scoring are sent to OpenAI. Requests use
store:false, and uncertain failed requests are not automatically repeated.
Provider policies and model availability can change, so researchers should
check the settings before using participant data in a new study.

3. Follow an offer through the code

In A1, code/A1-1.py combines the offer text, role, optional referenced previous
offer, general prompt and exercise files into one model request. The model
receives every active issue and option definition. It returns its interpretation
as JSON. code/A1-2.py checks that interpretation and uses the researcher-defined
values to calculate the scores. Preparing a request, interpreting an offer and
calculating points are separate steps; they are not three model calls.

In A2, code/A2-1.py first selects potentially relevant issue definitions. The
request includes exercise-specific reading instructions as well as the prompt
and role materials. After the model responds, code/A2-2.py applies custom rules,
checks the interpretation and calculates points. The current job scorer makes
one Luna call rather than escalating through progressively stronger models.

A2 uses a separate tutorial scorer. A long tutorial input can receive a second
reading by the same model. The job-specific corrections are not applied to it.
Its separate evaluation shows where more adaptation would be needed.

The exact A1 and A2 prompt files are in code/prompts/. A2's additional job
instructions are in code/frozen/A2_Reading_Rules.json. The architecture guide
explains what each prompt section does, where the custom rules are applied,
and what each script receives and returns. Keep these details in Appendix B;
Appendix C mainly helps readers find and use them.

4. Use the scripts directly

From the architecture folder, this command prepares a request without calling
a model:

    python code/score_offer.py --case-json code/examples/job_offer.json

To calculate scores from a saved interpretation, also without a model call:

    python code/score_offer.py --case-json code/examples/job_offer.json --interpretation-json code/examples/job_interpretation.json

For a live command-line call, set OPENAI_API_KEY in your environment and add
--live. The command-line scripts read the environment variable; the web app
also supports the .env convenience file. Select --architecture A2 or
--reasoning high as appropriate. Use code/score_tutorial_offer.py for the
tutorial. Each script also accepts --help.

To check the package without using an API key:

    python -m unittest discover -s code/tests -v

These tests check request preparation and scoring against saved examples. They
also check that the implementation and web app work after being copied to a
differently named folder. No extra Python packages are needed to run the app
or these scoring tests.

5. Read the exercise materials

The combined role-materials document introduces the main task and tutorial
before presenting their roles. It contains both private roles for researchers
to read. During a study, each negotiator should receive only their assigned role.

The scoring-table workbook is convenient to browse. The JSON files also provide
definitions, numerical domains, units and rules for calculating points between
the displayed examples. Those rules are used by the scorer. In fixed-9.json,
only the nine active issues belong to the fixed negotiation; other definitions
remain in the file for compatibility.

Study_Questionnaires.docx/.pdf brings together the questions used after the
negotiation and in the earlier role-feedback survey. The corresponding YAML
files retain the interface settings. Post_Negotiation_Analysis_Schema.json gives
the question wording used to label the analysis. Some deployment settings,
such as payment messages, are included alongside the substantive questions.

6. Inspect the validation spreadsheets

NOVA_Offer_Validation.xlsx contains 1,225 main-exercise inputs, each evaluated
with A1-low, A1-high and A2. Its Main sheet shows the offer, source, role,
scorer response, Type A and B judgments and review reasons. The same offer IDs
repeat across scorer blocks so readers can compare responses directly.

The Accuracy sheet calculates from the Y/N judgments. Changing a judgment
updates the count. The Prompts sheet records the instructions. The separate
NOVA_Tutorial_Validation.xlsx uses the same layout for 731 tutorial inputs,
including previous-offer context. It is not added to the main 1,225 denominator.

Type A means that a meaningful idea was missed or improperly left unscored.
A useful question can handle an essential missing detail, and an idea genuinely
absent from the table can be acknowledged without points. Type B means that an
unproposed issue was added, including a question that reveals an unrelated
optional idea. An input passes primary accuracy when neither error is present.

The main collection retains retries rather than deduplicating them. It includes
930 live calculator inputs, 294 offer answers from 98 completed feedback
surveys, and one research-assistant example. A calculator input was not
necessarily sent to the other negotiator. Use the separate sent-offer file to
study what happened during negotiations.

The judgments reflect model-assisted review and researcher corrections. Earlier
feedback also helped improve later scorer versions. They should not be described
as an independent blinded gold standard or a wholly untouched test set. The
saved files reproduce the recorded classifications; new model calls can differ.
Primary A/B accuracy does not independently verify every numerical mapping.

7. Reproduce the analyses

You can read or print Analysis.html without installing anything. To run the
calculations, open the validation folder, create and activate a Python virtual
environment, then install its requirements.txt. Run python analysis.py or
execute Analysis.ipynb from that folder. Neither makes model calls or requires
an API key. Results are written to results/ and figures/.

The notebook calculates accuracy and confidence intervals from the review
judgments. API usage records provide input, cached input and output tokens,
call counts and durations. The documented historical rates produce cost
estimates per 1,000 offers. These are operating-cost estimates based on the
observed use of caching, not reconstructed invoices or current price quotes.

For behavior, the trial file includes assigned pairs that did not complete
the task. The negotiation file identifies valid reciprocal negotiations and
early quits. The completed NOVA sample used in the paper contains 38 dyads.
Behavioral inclusion does not require a completed survey; survey comparisons
require valid pairs with both questionnaires and both answers to a measure.

Issue diversity counts distinct issues across submitted offers. Additional
diversity excludes the three required issues. Issue introduction means adding
an issue not previously mentioned after opening. Exploration means changing
the set relative to the union of both parties' latest offers. The notebook
recalculates these measures from submitted offers and produces the issue
frequency chart and NOVA-only diversity histogram.

The survey analysis reports means, SDs, confidence intervals and unadjusted
exploratory p values using dyad means. Subjective-value Q3 and Q5 are reversed.
Creative engagement and confidence use different response scales. Q29 asks
about feeling stuck; it is not a separate validated impasse measure. Exact
tutorial duration was unavailable, so preparation time is labelled as a proxy.

8. Privacy and details to check when writing

Participant information was de-identified before sharing. The public package
does not include Prolific IDs, contact details, demographic exports, exact event
timestamps, API keys or the list linking shared labels back to participants.
The originals remain private. Privacy_Review.md explains the checks and the
remaining risk that distinctive wording could make a response recognizable.

Two historical details are flagged in the analysis. The frozen 215-issue table
has no coffee entry, despite a later addition mentioned in the manuscript.
Some older agreement metadata also says scores must be strictly positive;
the analysis follows the researcher's rule that both scores can be zero or
above. The package notes these differences rather than quietly changing the
historical records.

For more detail, Methods.md explains the calculations and Data_Dictionary.md
explains the files. The development_records folder keeps earlier review prompts
and aggregate results so readers can follow how the work developed. Use the
main results folder for the current reported calculations.
